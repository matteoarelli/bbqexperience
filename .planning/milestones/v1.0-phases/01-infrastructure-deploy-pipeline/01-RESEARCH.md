## Summary

Phase 1 sets up the foundation: Strapi 5 with PostgreSQL running in Docker on the existing Hetzner server, all content types defined, i18n configured for EN/IT/ES, and a webhook-triggered rebuild pipeline for Astro. The Hetzner server already runs 24 containers with Caddy reverse proxy, PostgreSQL 16, adnanh/webhook listener, and has ample resources (8 CPU, 15GB RAM, 271GB free disk).

The key architectural insight is that this phase has TWO webhook flows: (1) GitHub push triggers adnanh/webhook to pull code and rebuild Docker images (existing pattern), and (2) Strapi content changes trigger a separate webhook to rebuild the Astro static site. Both use the adnanh/webhook listener on the server but serve different purposes.

**Primary recommendation:** Follow the existing deploy pattern exactly (git push -> adnanh/webhook -> deploy script), add Strapi + its own PostgreSQL database to the shared docker-compose.yml, configure Caddy for CMS subdomain, and set up a second webhook hook for Strapi content-change rebuilds.

### Pattern 1: Existing Deploy Pattern (Git Push -> adnanh/webhook)
**What:** GitHub webhook fires on push to main. adnanh/webhook on Hetzner receives it, validates HMAC-SHA256 signature, runs deploy script.
**When to use:** Every code change deployment.
**Verified on server:** All existing projects follow this pattern. hooks.json has entries with `payload-hmac-sha256` trigger rules matching `refs/heads/main`.
**Example deploy script** (based on existing servicecoach pattern):
```bash
#!/bin/bash
set -e
LOG="/opt/webhooks/logs/bbqexperience.log"
exec > >(tee -a "$LOG") 2>&1
echo "$(date "+%Y-%m-%d %H:%M:%S") -- Deploy bbqexperience iniziato"

APP_DIR="/opt/services/bbqexperience/app"
COMPOSE_DIR="/opt/services"

cd "$APP_DIR"
GIT_SSH_COMMAND="ssh -i /root/.ssh/github_bbqexperience" git pull origin main 2>&1

cd "$COMPOSE_DIR"

# Ricostruisci solo i container modificati
docker compose build bbqexperience-strapi 2>&1 | tail -5
docker compose up -d bbqexperience-strapi

# Ricostruisci sito statico Astro
/opt/webhooks/scripts/rebuild-bbqexperience-web.sh

docker image prune -f > /dev/null 2>&1
echo "$(date "+%Y-%m-%d %H:%M:%S") -- Deploy bbqexperience completato"
```

### Pattern 2: Strapi Content Webhook -> Astro Rebuild
**What:** Strapi fires HTTP POST on content publish/update/delete. A second adnanh/webhook hook receives this and triggers Astro rebuild.
**When to use:** Every content change in CMS.
**Key difference from Pattern 1:** This is NOT a GitHub webhook. Strapi sends its own format. The adnanh/webhook hook for this needs different trigger rules (no HMAC-SHA256 from GitHub, instead use a simple token match or Strapi's custom header).
**Implementation:**
1. Add a `bbqexperience-rebuild` hook in hooks.json that validates a secret token header
2. Configure Strapi (via admin panel) to POST to `http://host.docker.internal:9000/hooks/bbqexperience-rebuild` on entry.publish, entry.update, entry.delete events
3. The hook runs rebuild-bbqexperience-web.sh which builds Astro and copies output

```bash
#!/bin/bash
# rebuild-bbqexperience-web.sh
# Chiamato sia dal deploy (git push) sia dal webhook Strapi (content change)
set -e
LOG="/opt/webhooks/logs/bbqexperience.log"
echo "$(date "+%Y-%m-%d %H:%M:%S") -- Rebuild web iniziato" >> "$LOG"

WEB_DIR="/opt/services/bbqexperience/app/web"
OUTPUT_DIR="/opt/services/bbqexperience/dist"

cd "$WEB_DIR"
npm ci --production=false 2>&1 | tail -3
STRAPI_URL=http://localhost:1337 STRAPI_API_TOKEN=$STRAPI_TOKEN npm run build 2>&1 | tail -5

# Copia output build nella directory servita da Caddy
rm -rf "$OUTPUT_DIR.old"
[ -d "$OUTPUT_DIR" ] && mv "$OUTPUT_DIR" "$OUTPUT_DIR.old"
cp -r dist "$OUTPUT_DIR"

echo "$(date "+%Y-%m-%d %H:%M:%S") -- Rebuild web completato" >> "$LOG"
```

### Pattern 3: Strapi on Shared PostgreSQL
**What:** Use the existing PostgreSQL 16 container on the server. Create a dedicated database for Strapi.
**When to use:** This phase.
**Why:** The server already runs postgres:16-alpine with 200 max connections. Adding a `bbqexperience` database costs nothing and avoids running a second PostgreSQL instance.
**Setup:**
```bash
# Sul server, nel container postgres esistente
docker exec -it postgres psql -U postgres -c "CREATE DATABASE bbqexperience;"
docker exec -it postgres psql -U postgres -c "CREATE USER bbqexperience WITH PASSWORD 'secure_password';"
docker exec -it postgres psql -U postgres -c "GRANT ALL PRIVILEGES ON DATABASE bbqexperience TO bbqexperience;"
```

### Anti-Patterns to Avoid
- **Running a second PostgreSQL container:** The server already has one. Use it.
- **Using SQLite for Strapi:** Not suitable for production. Strapi recommends PostgreSQL.
- **Exposing Strapi port publicly:** Keep Strapi behind Caddy. Only Caddy faces the internet.
- **Configuring webhooks only via admin panel:** Webhook URL and headers should be documented in code/config so they survive database resets. Use `config/server.ts` for default headers.
- **Building Astro inside a Docker container:** Astro builds static HTML. Run `npm run build` directly on the host or in a build step, then serve the output via Caddy's `file_server`. No need for a running container.

**Key insight:** This phase is almost entirely configuration and wiring, not custom code. The server infrastructure already exists -- we are adding Strapi to an established pattern.

## Common Pitfalls

### Pitfall 1: Strapi Admin Panel Not Accessible After Deploy
**What goes wrong:** Strapi runs but admin panel returns 404 or blank page.
**Why it happens:** `url` in `config/server.ts` doesn't match the actual URL behind reverse proxy. Or Caddy doesn't proxy the `/admin` path correctly.
**How to avoid:** Set `url` in server config to the full public URL (e.g., `https://cms.bbqexperience.com`). Ensure Caddy proxies ALL paths (not just `/api`).
**Warning signs:** 404 on `/admin`, broken assets on admin panel.

### Pitfall 2: Uploads Not Persisting Across Container Restarts
**What goes wrong:** Uploaded images disappear after container restart/rebuild.
**Why it happens:** The `public/uploads` directory is inside the container and not volume-mounted.
**How to avoid:** Volume mount `./bbqexperience/uploads:/opt/app/public/uploads` in docker-compose.yml.
**Warning signs:** Images showing as broken after any container restart.

### Pitfall 3: Strapi Webhook Floods Causing Rebuild Storms
**What goes wrong:** Editing multiple content items triggers dozens of rebuilds simultaneously.
**Why it happens:** Strapi fires a webhook for every save/publish event. Batch edits = batch webhooks.
**How to avoid:** Add a debounce/cooldown to the rebuild script. Use a lockfile approach: if rebuild is running, skip new triggers. Or use a simple "last trigger wins" with a 30-second delay.
**Warning signs:** Multiple concurrent Astro builds consuming all server resources.

### Pitfall 4: Docker Network Connectivity Between Strapi and PostgreSQL
**What goes wrong:** Strapi can't connect to PostgreSQL.
**Why it happens:** Containers on different Docker networks can't communicate. The existing postgres is on the `internal` network.
**How to avoid:** Ensure `bbqexperience-strapi` service is on the `internal` network (same as postgres). Use `postgres` as the DATABASE_HOST (container name).
**Warning signs:** `ECONNREFUSED` errors on Strapi startup.

### Pitfall 5: Caddy auto_https Conflict
**What goes wrong:** Caddy tries to get certificates but fails because Cloudflare handles SSL.
**Why it happens:** The existing Caddyfile has `auto_https off` at the global level and listens on `:80`. This is intentional -- Cloudflare terminates SSL.
**How to avoid:** Follow the existing pattern: add new site handlers inside the `:80` block with host matchers. Do NOT add a separate `https://cms.bbqexperience.com` block.
**Warning signs:** Caddy refusing to start, certificate errors in logs.

### Pitfall 6: APP_KEYS / JWT_SECRET Not Set
**What goes wrong:** Strapi refuses to start or sessions break unpredictably.
**Why it happens:** These secrets are required in production but easy to forget in env setup.
**How to avoid:** Generate secure random values for APP_KEYS, JWT_SECRET, ADMIN_JWT_SECRET, and API_TOKEN_SALT. Document in .env.example.
**Warning signs:** Strapi startup errors mentioning "missing secrets" or "undefined APP_KEYS".

## Strapi 5 Webhook Events Reference

| Event | Fires When | Use For |
|-------|-----------|---------|
| `entry.create` | New content entry created | Rebuild (if auto-publish) |
| `entry.update` | Existing entry modified | Rebuild |
| `entry.delete` | Entry deleted | Rebuild |
| `entry.publish` | Draft published | **Primary rebuild trigger** |
| `entry.unpublish` | Published entry unpublished | Rebuild (remove page) |
| `media.create` | Media uploaded | Usually no rebuild needed |
| `media.update` | Media replaced | Optional rebuild |
| `media.delete` | Media deleted | Optional rebuild |

**Recommendation:** Subscribe to `entry.publish`, `entry.unpublish`, and `entry.delete` only. These are the events that affect the public site. Avoid `entry.create` and `entry.update` (drafts should not trigger rebuilds).
