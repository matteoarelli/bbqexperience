## Summary

Phase 10 closed DEBT-03 partially: 9/15 baseline pages now score ≥90 on Lighthouse Performance after LCP preload + `fetchpriority=high` + CLS width/height + inline CSS + lazy GSAP fixes. The residual 6 pages (home-en/it/es, review-en/es, blog-en) are all LCP-bound on the same failure mode: the Strapi origin serves raw JPEGs at full resolution (~100–300 KB, sometimes >600 KB savings per page per the Lighthouse `image-delivery-insight` audit) to every device regardless of viewport. No amount of preload/fetchpriority can fix a ~110 KB `.jpg` transfer on simulated Slow 4G mobile — the fix has to be **format negotiation (AVIF/WebP) + width-clamped responsive sizes**.

The canonical CLAUDE.md-compliant solution is **Cloudflare Image Transformations** (the `/cdn-cgi/image/` URL-rewrite product, historically "Image Resizing", now merged into the "Cloudflare Images" umbrella as of mid-2024). It is a zero-new-dependency, account-level feature: enable it in the dashboard, add `cms.bbq-experience.com` as an allowed source origin, and rewrite the output of `getStrapiMediaURL()` (and its callers that generate `srcset`) to produce URLs of the form `https://bbq-experience.com/cdn-cgi/image/width=W,quality=75,format=auto/https://cms.bbq-experience.com/uploads/<name>.jpg`. 5,000 unique transforms/month are free; a site of ~300 media assets × 5 srcset widths = ~1,500 cached transforms sits well inside that budget. [CITED: developers.cloudflare.com/images/pricing]

**BLOCKING PREREQUISITE (verified this session, 2026-04-16):** `bbq-experience.com` is currently DNS-only (grey cloud) on Cloudflare — the `A` record points directly to Hetzner `204.168.153.43`, origin responses carry `Via: 1.1 Caddy` with NO `cf-ray` / `cf-cache-status` headers. A test request to `https://bbq-experience.com/cdn-cgi/image/width=300,format=auto/https://cms.bbq-experience.com/uploads/test.jpg` returns the Caddy 404, not a Cloudflare edge response — confirming the zone is not proxied. Image Transformations require the zone serving the transform URL to be proxied (orange cloud). **The planner MUST pause for user decision before code work begins:** flipping the cloud from grey to orange is a 2-click operation in Cloudflare DNS dashboard, but it changes request routing for the entire site and needs Matteo's explicit approval. [VERIFIED: curl against production]

**Primary recommendation:** Ship in two plans — (1) user-checkpoint + enable transformations + switch root zone to proxied + orange-cloud verification via `cf-ray` header; (2) rewrite `getStrapiMediaURL()` + add `buildSrcset()` helper + wire srcset into the 5 hot templates + re-measure + update SUMMARY.md. Do NOT use the paid "Cloudflare Images" storage product (uploads to `imagedelivery.net`) — it's a different product and would duplicate Strapi's media library. Do NOT adopt Astro `<Image>` for CMS media: Astro's built-in Sharp pipeline only runs at build-time; this is an SSR site (`output: 'server'`) and Strapi content changes without a rebuild trigger. [VERIFIED: astro.config.mjs line 8 `output: 'server'`]

### Pattern 1: URL-rewrite helper (replaces raw pass-through)

**What:** Rewrite `getStrapiMediaURL()` to emit `/cdn-cgi/image/…` prefix transparently. Keep legacy behaviour behind an option flag (`raw: true`) for the og:image and favicon cases where we do NOT want transformation.

**When to use:** Every `<img src>` and `<img srcset>` in a template that renders a Strapi-sourced image.

**When NOT to use (raw):** OpenGraph/Twitter card meta (Facebook/Twitter scrapers dislike redirected/resized URLs and will re-fetch); favicons; SVG logos; `<link rel=icon>`.

**Example:**

```typescript
// Source: adapted from developers.cloudflare.com/images/transform-images/transform-via-url/
// Helper per la risoluzione degli URL media Strapi attraverso Cloudflare Image Transformations.
// Pattern: <zone>/cdn-cgi/image/<options>/<absolute-source-url>
//   - zone = bbq-experience.com (deve essere PROXIED orange-cloud su Cloudflare)
//   - source = cms.bbq-experience.com/uploads/<file> (deve essere in "allowed origins")
//   - options = comma-separated, NO spazi (es. "width=640,quality=75,format=auto")

const PUBLIC_CMS_URL = import.meta.env.PUBLIC_CMS_URL || 'https://cms.bbq-experience.com';
const TRANSFORM_ZONE = 'https://bbq-experience.com';

interface TransformOptions {
  width?: number;
  quality?: number;       // 1-100 o 'high'|'medium-high'|'medium-low'|'low'
  format?: 'auto' | 'avif' | 'webp' | 'jpeg';
  fit?: 'cover' | 'contain' | 'scale-down' | 'crop';
  raw?: boolean;          // bypassa la trasformazione (per og:image, favicon)
}

export function getStrapiMediaURL(
  media: StrapiMedia | null | undefined,
  opts: TransformOptions = {}
): string | null {
  if (!media?.url) return null;

  // URL assoluto della sorgente (Strapi)
  const sourceUrl = media.url.startsWith('http')
    ? media.url
    : `${PUBLIC_CMS_URL}${media.url}`;

  // Bypass: og:image, favicon, casi in cui la trasformazione non aiuta
  if (opts.raw) return sourceUrl;

  // Costruzione opzioni Cloudflare (ordine deterministico per caching)
  const parts: string[] = [];
  if (opts.width) parts.push(`width=${opts.width}`);
  parts.push(`quality=${opts.quality ?? 75}`);
  parts.push(`format=${opts.format ?? 'auto'}`);
  if (opts.fit) parts.push(`fit=${opts.fit}`);

  // Se nessuna width -> nessuna trasformazione utile, fallback raw
  if (!opts.width) return sourceUrl;

  return `${TRANSFORM_ZONE}/cdn-cgi/image/${parts.join(',')}/${sourceUrl}`;
}

// Responsive srcset per <img srcset> secondo le width consigliate da Cloudflare
// [CITED: developers.cloudflare.com/images/transform-images/make-responsive-images/]
export function buildStrapiSrcset(
  media: StrapiMedia | null | undefined,
  widths: number[] = [320, 640, 960, 1280]
): string | null {
  if (!media?.url) return null;
  return widths
    .map((w) => `${getStrapiMediaURL(media, { width: w })} ${w}w`)
    .join(', ');
}
```

### Pattern 2: Template wiring (the hot 5 pages)

**What:** Emit both `src` (fallback) and `srcset` + `sizes` so browsers pick the optimal variant.

**Example (`FeaturedHero.astro`):**

```astro
---
import { getStrapiMediaURL, buildStrapiSrcset } from '@lib/media';
const cover = mainPost?.cover_image;
const coverSrc = getStrapiMediaURL(cover, { width: 1280, quality: 75 });
const coverSrcset = buildStrapiSrcset(cover, [640, 960, 1280, 1600]);
---
<img
  src={coverSrc}
  srcset={coverSrcset}
  sizes="(max-width: 768px) 100vw, 1280px"
  alt={cover?.alternativeText || mainPost.title}
  width="1600"
  height="900"
  loading="eager"
  decoding="async"
  fetchpriority="high"
/>
```

### Pattern 3: LCP preload with matching transformed URL

**What:** The `<link rel=preload>` in `BaseLayout.astro` MUST point to the SAME transformed URL the `<img>` renders with — otherwise the browser double-fetches (preload raw + render transformed), hurting LCP instead of helping.

**Example (call site in `web/src/pages/en/index.astro`):**

```typescript
// Prima: lcpPreloadUrl = getStrapiMediaURL(featuredRes.data[0]?.cover_image) || '';
// Dopo: stessa URL che FeaturedHero usa per src (width=1280, quality=75, format=auto)
const lcpFeatured = featuredRes.data[0]?.cover_image;
const lcpPreloadUrl = getStrapiMediaURL(lcpFeatured, { width: 1280, quality: 75 }) || '';
```

Then pass to `BaseLayout preloadImage={lcpPreloadUrl}`.

### Anti-Patterns to Avoid

- **Transforming the og:image URL** — Facebook/X scrapers may not follow the transform URL correctly and may cache a broken preview. Keep `ogImage` pointing at `/api/og-image?…` (server-generated OG card, already does this) or raw Strapi URL via `{raw: true}`.
- **Transforming SVGs** — Cloudflare does NOT transform SVG (documented). Pass `{raw: true}` or skip entirely for SVGs.
- **Transforming `favicon.svg`** — Not a CMS asset. Never touched by `getStrapiMediaURL`, so naturally out-of-scope.
- **Mismatched preload vs render URL** — causes double-download; always match the preload URL's option string to one of the srcset widths the renderer will pick (usually the largest or smallest depending on viewport).
- **Including spaces in the option list** — Cloudflare silently rejects. Always comma-only separator, no spaces. [CITED: developers.cloudflare.com/images/transform-images/transform-via-url/]
- **Using `width=auto`** — requires `Accept-CH: Viewport-Width` client-hint header and browser support; brittle. Explicit width list is more predictable.
- **Rewriting the body markdown `<img>` tags in `renderMarkdown()`** — out of scope for this phase. The blog-en 404-fetch test this session shows the currently-failing pages do NOT rely on inline markdown body images for LCP (the LCP element is always the cover). Defer markdown-body rewriting to a later phase if needed.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Image resizing / format conversion | A Node worker with Sharp on Hetzner | Cloudflare `/cdn-cgi/image/` | Edge-cached, zero origin CPU, zero maintenance, handles AVIF fallback to WebP fallback to JPEG automatically based on `Accept` header |
| Responsive srcset selection | Custom device-detection code in middleware | Browser's native `<img srcset sizes>` + Cloudflare's `format=auto` | Browsers are better at this than servers; format=auto reads the client `Accept` header |
| Image dimension metadata | Reading image EXIF server-side | Strapi v5 already surfaces `width`/`height` on `StrapiMedia` (see `types.ts:25-35`) — wire it through to the `<img>` attributes in a future iteration | Already present in the upstream payload |
| Cache invalidation on content change | Custom purge script | Cloudflare's 30-day default cache + automatic revalidation on origin `Cache-Control` | Matteo changes images rarely; Strapi edits get a new `documentId`/filename so new transforms are fresh URLs. Only purge on full re-upload |

**Key insight:** The Lighthouse sub-90 gap is **bandwidth, not CPU**. The fix lives at the network edge, not in the application. The entire implementation is effectively a 40-line helper change + dashboard config — every other approach (Strapi Sharp, Astro Image, custom worker) adds code/ops burden for the same or worse outcome.

## Common Pitfalls

### Pitfall 1: Zone is DNS-only (grey cloud) — THE blocker

**What goes wrong:** Request to `https://bbq-experience.com/cdn-cgi/image/…/foo.jpg` hits Caddy directly and returns 404 (because Caddy has no route for `/cdn-cgi/…`). The entire feature is silently nonfunctional.
**Why it happens:** The `/cdn-cgi/image/` endpoint is implemented at the Cloudflare edge, NOT at the origin. Only proxied (orange-cloud) requests traverse the edge.
**How to avoid:** **Verify orange-cloud BEFORE writing any code.** Plan Task 1 must be a dashboard checkpoint that Matteo approves (this changes request routing for the entire site — TLS terminates at CF, you get a new `cf-ray` header, `Via: 1.1 Caddy` disappears). Verification command:
```bash
curl -sI https://bbq-experience.com/en/ | grep -iE "cf-ray|server:|via:"
# Before (today): Via: 1.1 Caddy        ← grey cloud
# After flip:     cf-ray: <id>          ← orange cloud, transformations work
#                 server: cloudflare
```
**Warning signs:** `Via: 1.1 Caddy` in response headers; A-record resolves to `204.168.153.43` via public resolver (dns.google).

### Pitfall 2: CSP `img-src` does not include the zone's own origin

**What goes wrong:** Browser blocks the transformed image with CSP violation: "Refused to load the image 'https://bbq-experience.com/cdn-cgi/image/…' because it violates the Content Security Policy directive 'img-src 'self' cms.bbq-experience.com data: …'". [VERIFIED: CSP-Report-Only header from curl this session]
**Why it happens:** The current CSP allows `cms.bbq-experience.com` and `'self'` — but `'self'` is the page's origin. Since transformed URLs ARE served from the page's origin (`bbq-experience.com/cdn-cgi/image/…`), they match `'self'`. **Actually this is fine** — re-verifying: the transformed URL's scheme+host is `https://bbq-experience.com` which equals `'self'` for any page served from `bbq-experience.com`. No CSP change needed. [VERIFIED via CSP spec: `'self'` matches the exact origin of the document]
**How to avoid:** Confirm post-deploy by checking browser DevTools → Console for any CSP violations on the 5 re-measured pages. If the current CSP is Report-Only (which it is — `Content-Security-Policy-Report-Only` header), no enforcement happens during this phase.
**Warning signs:** CSP report-URI logs a new hostname in violations (monitor the first 24h).

### Pitfall 3: preload URL ≠ srcset URL picked by browser

**What goes wrong:** `<link rel=preload href="…width=1280…">` but the browser picks `…width=640…` from srcset → two fetches, preload wasted, LCP gets WORSE.
**Why it happens:** Preload doesn't know the viewport; srcset picks the right variant. If they don't match, the preload is dead weight.
**How to avoid:** For mobile-dominant LCP (which is exactly what we're measuring — Lighthouse mobile throttled), preload the **mobile** width (640 or 960), not 1280. Or drop the preload for variants that have a srcset (the srcset itself is already an early discovery hint with `fetchpriority=high`).
**Warning signs:** Lighthouse reports "fetch via preload was unused" or LCP DELTA is negative after the change.

### Pitfall 4: Cloudflare source-origin allowlist rejects the subdomain

**What goes wrong:** Transform URL returns error 9420 ("source not allowed") because `cms.bbq-experience.com` is not in the Sources config.
**Why it happens:** Default allows only same-zone same-subdomain. `cms.` subdomain requires explicit listing. [CITED: developers.cloudflare.com/images/transform-images/sources/]
**How to avoid:** Dashboard → Images → Transformations → Sources → Add origin → Domain: `cms.bbq-experience.com`. Alternative: add `*.bbq-experience.com` wildcard for future subdomains.
**Warning signs:** 400 responses from the transform URL with Cloudflare error page mentioning "source origin not allowed" or error code `9420`.

### Pitfall 5: Cache stampede on first deploy

**What goes wrong:** Ship the change, immediately every page for every visitor triggers a fresh transform for every srcset width — 5,000 free transforms/month get eaten in an hour on a site with even modest traffic.
**Why it happens:** Zero warm cache at deploy time. Each unique `(origin + options)` combo counts once per month.
**How to avoid:** Cloudflare caches transforms for ~30 days by default; a burst only matters for unique combos. With 5 widths × ~60 unique cover images across 3 locales = ~300 unique transforms. Safely under 5k. **But:** if we also transform gallery images (review pages have `gallery[]` of ~5-10 images each × 2 widths × 25 products = 500 more transforms), we're at ~800/month — still safe. Monitor first month via Cloudflare dashboard's "Transformations" usage graph.
**Warning signs:** Cloudflare dashboard "Transformations" tab shows rising transforms/day without a content change; Lighthouse re-measurement shows some images returning 9422 (cap hit).

### Pitfall 6: OG image transformation breaks social previews

**What goes wrong:** Transformed URLs have query-string-like parameters in the path; some social scrapers (LinkedIn, older Facebook) choke on them or cache the 404 while the transform warms.
**Why it happens:** Social scrapers are not browsers and sometimes have brittle URL parsers.
**How to avoid:** The review pages use `ogImage={/api/og-image?...}` (SSR-generated card — already optimized, not a Strapi URL). Blog/tutorial/recipe pages use `ogImage={coverImageUrl}` — for THESE, pass `{raw: true}` so og:image keeps pointing at the raw Strapi URL. [VERIFIED: grep of `ogImage=` in `web/src/pages`]
**Warning signs:** Slack/Discord/Twitter link-unfurl shows a broken image where before it worked.

## Open Questions

1. **Should this phase also wire Strapi `width`/`height` metadata through to the `<img>` attributes, replacing the hardcoded `1600×900`?**
   - What we know: The `StrapiMedia` type surfaces `width`/`height` directly (`types.ts:25-35`); Plan 10-05-SUMMARY.md explicitly calls it out as "future enhancement".
   - What's unclear: Does the hardcoded 1600×900 interact badly with responsive srcset? The aspect-ratio mismatch (actual 4:3 image served with 16:9 declared) can cause subtle CLS regression.
   - Recommendation: Out of scope for 10.1; stay focused on the image-delivery fix. Add to backlog as a Phase 11 polish.

2. **Should we transform markdown body images too (via `renderMarkdown` post-processor)?**
   - What we know: The current `renderMarkdown()` pipeline could be extended with a regex pass that rewrites `<img src="https://cms.bbq-experience.com/…">` to the transformed URL.
   - What's unclear: Do any of the 6 failing pages have body images contributing to LCP? (Probed blog-en: no.)
   - Recommendation: Defer. If re-measurement shows residual gap from body images, open a targeted follow-up plan.

3. **Should we harden against an eventual 9422 (cap-exceeded) error by adding a fallback to raw URL?**
   - What we know: Free plan cap is 5k/month; our estimate is 300-800/month. Wide safety margin.
   - What's unclear: If traffic patterns change (e.g., new viral post causes a spike on a rarely-cached image), could a warm cache still save us? Yes — cached transforms don't count against the cap.
   - Recommendation: Defer. Add a Cloudflare Analytics alert rule if usage approaches 4k/month (manual observability, not code).

4. **Should the transform zone (`https://bbq-experience.com`) be env-ized?**
   - What we know: Hardcoded constant is fine for a single-environment production site (dev runs against localhost Strapi; transformations don't apply locally anyway).
   - What's unclear: Preview deploys or staging environments could want a different zone.
   - Recommendation: Hardcode for now with a comment flagging future env-ization; add `PUBLIC_IMAGE_TRANSFORM_ZONE` only if a staging need materializes.
