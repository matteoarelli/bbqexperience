# Phase 10.1: Code Review Report

**Reviewed:** 2026-04-16
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Phase 10.1 introduce Cloudflare Image Transformations tramite due helper in `web/src/lib/media.ts` (`getStrapiMediaURL` + `buildStrapiSrcset`) e li wire in 12 template (3 locale × 4 tipi di pagina). L'implementazione e funzionalmente corretta, backward compatible (tutti i ~29 call-site senza `opts` ricevono URL raw) e ha copertura test ragionevole (14 test, inclusi ordine deterministico option, bypass `raw`, encoding spazi).

Il threat model documentato in 10.1-RESEARCH.md (T-10.1-02/05/06/09) e rispettato a livello macro: og:image e Article/Review JSON-LD usano `{raw:true}` per compatibilita scraper social (T-10.1-06), cache-key e deterministico via ordine fisso degli option, preload e src combaciano sulla stessa width (1280) per evitare double-fetch (T-10.1-09).

Sono emerse 4 warning e 7 info. Le warning principali sono:

1. Mancanza di validazione hostname sul source URL (difesa-in-profondita per T-10.1-05 / SSRF)
2. Encoding via `encodeURI` non copre query string / fragment
3. Query Strapi duplicata per il LCP preload nelle 3 homepage (costo runtime, non correttezza)
4. `preloadImage=""` come stringa vuota invece che `null` (potenziale preload spurio)

Nessuna critical issue. Il layer CF Sources allowlist (verificato 2026-04-16) mitiga gli scenari SSRF a livello edge, riducendo la severity.

## Warnings

### WR-01: Mancanza validazione hostname sul source URL (defense-in-depth T-10.1-05)

**File:** `web/src/lib/media.ts:54-56`
**Issue:** `getStrapiMediaURL` accetta qualsiasi URL assoluto presente in `media.url` (`media.url.startsWith('http')`) e lo inserisce direttamente come source path del `/cdn-cgi/image/`. Se un attaccante con accesso Strapi (admin, import da terze parti, content-queue automatizzata) inserisce `url: "https://evil.com/tracker.jpg"`, il sito emettera `<img src="https://bbq-experience.com/cdn-cgi/image/.../https://evil.com/tracker.jpg">`. Attualmente il Cloudflare Sources allowlist (`cms.bbq-experience.com`, `bbq-experience.com`) rifiuta queste origini a livello edge (verificato via curl in 10.1-01-SUMMARY.md), quindi l'impatto pratico e bloccato. Ma il codice client non ha guardia indipendente: una modifica di config CF (disabilitare Sources allowlist) trasformerebbe il sito in open-proxy silenzioso. Threat T-10.1-05 e documentato come "mitigato a livello CF" ma senza difesa in profondita lato app.
**Fix:**
```ts
// Validazione allowlist hostname lato app (defense-in-depth vs T-10.1-05)
const ALLOWED_SOURCE_HOSTS = new Set([
  'cms.bbq-experience.com',
  'bbq-experience.com',
]);

// Dentro getStrapiMediaURL, dopo il calcolo di sourceUrl:
if (opts.width && !opts.raw) {
  try {
    const host = new URL(sourceUrl).hostname;
    if (!ALLOWED_SOURCE_HOSTS.has(host)) {
      // Host non in allowlist -> fallback raw (CF rifiuterebbe comunque)
      return sourceUrl;
    }
  } catch {
    return sourceUrl; // URL malformato -> bypass
  }
  // ... prosegui con costruzione /cdn-cgi/image/...
}
```
In alternativa, estrarre l'allowlist da env var (es. `PUBLIC_CF_TRANSFORM_SOURCES`) per mantenerla sincronizzata con la config CF.

### WR-02: `encodeURI` non gestisce query string e fragment nel source URL

**File:** `web/src/lib/media.ts:77`
**Issue:** `encodeURI(sourceUrl)` encoda spazi e caratteri non-ASCII (correttamente mitigando tampering su nome file), ma lascia intatti `?`, `#`, `&`, `=`, `,`. Se un `media.url` Strapi contiene una query string (es. signed URL con `?token=abc`) o un fragment, questi caratteri vengono passati letteralmente a Cloudflare. `,` e `=` sono i separatori degli option CF — Cloudflare parsa left-to-right fino al primo `/` dopo `/cdn-cgi/image/`, quindi non c'e collisione di parsing, ma il comportamento con URL con query string non e testato ne documentato. Inoltre un `#` nel source URL troncherebbe la richiesta edge lato CF.
**Fix:** Test + possibile `encodeURIComponent` parziale sul path preservando `/` e `:` separatori:
```ts
// Esempio di test da aggiungere in media.test.ts:
it('gestisce URL con query string (signed upload)', () => {
  const media = { url: '/uploads/hero.jpg?token=sig123' } as any;
  const result = getStrapiMediaURL(media, { width: 640 });
  expect(result).toContain('/cdn-cgi/image/');
  // Documenta comportamento: query string passa intatta al source
  expect(result).toContain('?token=sig123');
});

it('strip fragment dal source URL', () => {
  const media = { url: '/uploads/hero.jpg#section' } as any;
  const result = getStrapiMediaURL(media, { width: 640 });
  // Fragment non viene inviato al server -> deve essere rimosso o encoded
  expect(result).not.toContain('#section');
});
```
Se i test falliscono, aggiungere pre-processing:
```ts
// Rimuovi fragment (client-only) prima di costruire l'URL CF
const cleanSource = sourceUrl.split('#')[0];
const encodedSource = encodeURI(cleanSource);
```

### WR-03: Query Strapi duplicata per il LCP preload nelle 3 homepage

**File:** `web/src/pages/en/index.astro:69-81`, `web/src/pages/it/index.astro:69-81`, `web/src/pages/es/index.astro:69-81`
**Issue:** Le tre homepage eseguono una chiamata Strapi EXTRA (filtri `featured: $eq: true`, `pageSize: 1`) solo per ottenere il cover URL da usare come `preloadImage`. `FeaturedHero` fa gia la stessa query (con `pageSize: 3`), quindi e un roundtrip duplicato per ogni SSR. Il commento giustifica con "Strapi cacha la risposta a livello CDN" ma SSR genera ogni volta una fetch verso `cms.bbq-experience.com`. Con il deploy attuale (SSR Astro) questo raddoppia la latenza TTFB della home.
**Fix:** Esporre l'URL preload via prop/slot da `FeaturedHero` oppure sollevare la fetch fuori dal componente (una sola chiamata, condivisa):
```ts
// Opzione 1: esporta un helper shared
// src/lib/featured.ts
export async function getFeaturedMainImage(locale: Locale) {
  const res = await fetchCollection<StrapiBlogPost>('blog-posts', {
    locale,
    filters: { featured: { $eq: true } },
    populate: 'cover_image',
    sort: 'published_date:desc',
    pageSize: 3, // stessa del componente
  });
  return {
    posts: res.data,
    lcpImageUrl: getStrapiMediaURL(res.data[0]?.cover_image, { width: 1280, quality: 75 }) || '',
  };
}

// In index.astro:
const { posts, lcpImageUrl } = await getFeaturedMainImage(locale);
// Passa posts a FeaturedHero via prop per evitare la seconda fetch
<FeaturedHero posts={posts} locale={locale} translations={translations} />
```

### WR-04: `preloadImage=""` stringa vuota propagata a BaseLayout

**File:** `web/src/pages/en/reviews/[slug].astro:79`, `web/src/pages/it/recensioni/[slug].astro:78`, `web/src/pages/es/resenas/[slug].astro:78`, `web/src/pages/en/blog/[slug].astro:75`, `web/src/pages/it/blog/[slug].astro:74`, `web/src/pages/es/blog/[slug].astro:74`, `web/src/pages/en/index.astro:90`, `web/src/pages/it/index.astro:90`, `web/src/pages/es/index.astro:90`
**Issue:** Tutti i chiamanti usano il pattern `preloadImage={coverImage || ''}` invece di `preloadImage={coverImage || undefined}`. Se `BaseLayout` emette `<link rel="preload" as="image" href={preloadImage}>` senza guardia `{preloadImage && ...}`, ne risulta `<link rel="preload" href="">` che in alcuni browser triggera una fetch della pagina corrente (self-request). Non posso verificare il comportamento effettivo di BaseLayout da questo scope di review, ma il pattern e incoerente e rischioso.
**Fix:** Usare `undefined` invece di stringa vuota e verificare che BaseLayout abbia guardia:
```ts
// In ogni chiamante:
preloadImage={coverImage || undefined}

// In BaseLayout (da verificare):
{preloadImage && <link rel="preload" as="image" href={preloadImage} fetchpriority="high" />}
```

### IN-02: Hardcoded `TRANSFORM_ZONE` senza env var

**File:** `web/src/lib/media.ts:13`
**Issue:** `const TRANSFORM_ZONE = 'https://bbq-experience.com'` e hardcoded. Un ambiente di staging (es. `staging.bbq-experience.com`) non avrebbe le sue immagini trasformate via `bbq-experience.com` — la CF Sources allowlist lo rifiuterebbe, oppure (peggio) le immagini di staging si mescolerebbero con la cache CF di produzione.
**Fix:** Gia documentato come "Open Question 4" in 10.1-RESEARCH.md ("env-izzazione rimandata a futura iterazione"). Accettabile per v1. Suggerito per 10.2:
```ts
const TRANSFORM_ZONE = import.meta.env.PUBLIC_CF_TRANSFORM_ZONE || 'https://bbq-experience.com';
```

### IN-03: Test coverage mancante per alcuni pattern critici

**File:** `web/src/lib/media.test.ts`
**Issue:** Test non verificano direttamente:
- `buildStrapiSrcset` emette URL con prefisso `/cdn-cgi/image/` (inferito, non asserito)
- Comportamento con `media.url` contenente query string o fragment (cfr WR-02)
- Comportamento con `opts.width = 0` o negativo (edge case — CF rifiuterebbe)
- `widths` array vuoto in `buildStrapiSrcset` (ritorna stringa vuota, puo creare attribute `srcset=""` invalid)
**Fix:**
```ts
it('buildStrapiSrcset emette URL /cdn-cgi/image/ per ogni width', () => {
  const media = { url: '/uploads/hero.jpg' } as any;
  const result = buildStrapiSrcset(media, [320, 640]);
  const entries = result!.split(', ');
  entries.forEach((e) => expect(e).toContain('/cdn-cgi/image/'));
});

it('buildStrapiSrcset ritorna stringa vuota per widths array vuoto', () => {
  const media = { url: '/uploads/hero.jpg' } as any;
  expect(buildStrapiSrcset(media, [])).toBe('');
  // Valuta se preferire null per coerenza con il resto dell'API
});

it('getStrapiMediaURL ignora width 0 o negativa', () => {
  const media = { url: '/uploads/hero.jpg' } as any;
  expect(getStrapiMediaURL(media, { width: 0 })).not.toContain('/cdn-cgi/image/');
  expect(getStrapiMediaURL(media, { width: -10 })).not.toContain('/cdn-cgi/image/');
});
```

### IN-05: Test usano `as any` per mockare `StrapiMedia`

**File:** `web/src/lib/media.test.ts:25,30,34,52,57,71,82,93,101,110,137,146,160,173`
**Issue:** I test costruiscono mock come `{ url: '...' } as any` invece di avere un factory tipizzato. Accettabile per il tipo `StrapiMedia` che ha molti campi required, ma perde la type safety sui cambi di schema (es. se domani `StrapiMedia.url` diventa `string | null` i test continuano a passare ma il runtime non gestisce il null).
**Fix:**
```ts
// Helper factory tipizzato
const makeMedia = (overrides: Partial<StrapiMedia> = {}): StrapiMedia => ({
  id: 1,
  name: 'test.jpg',
  url: '/uploads/test.jpg',
  alternativeText: null,
  width: 1920,
  height: 1080,
  formats: null,
  ...overrides,
});

// Uso:
const media = makeMedia({ url: '/uploads/hero.jpg' });
```

**Issue:** L'index usa `lcpPreloadUrl` (gia stringificato con `|| ''` alla linea 80) mentre gli slug usano `coverImage || ''`. Non e un bug ma rende piu faticoso un refactor futuro. Collegato a WR-04.

### IN-07: Width ladder inconsistente tra hero (1600) e card (960)

**File:** `web/src/components/content/FeaturedHero.astro:46`, `web/src/components/content/ContentLayout.astro:43`, `web/src/components/home/ReviewCard.astro:23`
**Issue:** Hero usa `[640, 960, 1280, 1600]` mentre review card usa `[320, 640, 960]`. Un iPhone 15 Pro Max con DPR 3 e viewport 430px, che mostra una card a 100vw (max-width: 640px nel sizes), richiederebbe 1290w — ma il max disponibile e 960w. Il browser sceglie 960w, undersampling visibile su schermi retina di fascia alta. Non e un bug di correttezza (il rendering funziona), e una scelta di bandwidth.
**Fix:** Valutare se aggiungere `1280w` alla ladder delle card per coprire DPR3 mobile:
```ts
// In ReviewCard.astro e tutorial card nelle home:
const imageSrcset = buildStrapiSrcset(sourceMedia, [320, 640, 960, 1280]);
```
Impatto bandwidth: stimato +15-20% su connessioni 4G retina. Da misurare con un A/B Lighthouse prima di modificare.
